# 讲解规则

这份规则是模块讲解页的规格。`/delivery-brief:brief` 运行时先读它，再写讲解源文件。改讲法时只改这里。

## 读者与目标

读者是懂技术的程序员，主要是用户本人；他没看过这次的代码。讲解要让他**几分钟**看懂四件事：这次造了什么、为什么这样造、
几块东西怎么串起来、哪里要他判断。讲解只摆事实，**不给代码质量打分**，也不替代独立审查。

## 事实从哪来

`brief_facts.py` 的 JSON 是唯一的数字来源。常用字段：

- `range.base`／`range.head`：范围起止（base 不含）；`range.source`：`inferred-spec-guard`（按 spec-guard 文件约定推断）或 `explicit`；
  `range.basis.laterModuleCommits`：终点之后仍改模块文件的提交；`range.basis.openItemsAtHead`：HEAD 上还没勾的 todo 项。
- `commits[]`：`sha`、`short`、`subject`、`date`、`files`；`files[]`：`path`、`status`（A/M/D/R）、`added`、`deleted`、`binary`。
- `module.spec.acs[]`：`id`（无编号时为 null）、`text`；`module.todo.atEnd` 是范围终点那一刻的 todo，`atHead` 是现在的
  （验收后的发版勾选只在 `atHead` 里）；每项有 `text`、`checked`、`kind`（gate／report／task）、`deferred`。
- `usageDraft`：模块所属草案的 `file`、`milestone`、`usages`、`entries[]`（`entry`、`does`）。
- `links.kind`：`github` 或 `local`；`links.workingTreeMatchesEnd` 为 `false` 时，本机链接打开的是工作区文件，行号可能和终点提交
  对不上——渲染脚本会在页头提示，你写行号时仍以终点提交为准。

用法：

- 提交数、文件数、增删行、文件表、提交表、范围、来源（推断／指定）、进行中或已发版，**由渲染脚本放进页头和附录，你不要在正文里重写这些数字**；
  正文需要提到时写「见附录」或引用文件。
- `module.spec.acs` 是 AC 列表；`module.todo.atEnd`／`atHead` 是两个时刻的勾选；`usageDraft` 是计划的入口；`warnings` 渲染脚本会放到页头。
- `range.basis.laterModuleCommits`、`openItemsAtHead` 非空时，要在「需要你判断的」里说明它们意味着什么（例如发版收尾、里程碑停点还没做）。

## 读取策略

讲解要读代码，但不能整读：一次讲解的 diff 常有几万 token，被改文件全文常有几十万。按这个顺序：

1. 读 facts：范围、提交标题、文件表、AC、todo、用法草案。
2. 读 Spec 与 Plan（`spec/<id>.md`、`tasks/<id>/plan.md`，读**终点提交上的版本**），只为知道「本来要做什么」；**不拿它们的原话当证据**。
3. 读 diff：`git -C <项目> diff -M <base> <head> -- <文件>`，按文件读，先读新增的源码与测试，再读修改，最后扫文档。
   单个文件 diff 超过约 400 行时，先读 `--stat` 和函数签名，再挑关键片段。
4. 需要上下文时读文件片段：`git -C "$PROJECT" show "${HEAD}:${FILE}" | sed -n '<起>,<止>p'`，只读你要引用的那一段及前后几行。
   读的是**终点提交上的版本**，不是工作区。变量写成 `"${HEAD}:${FILE}"`：在 zsh 里 `$H:path` 会被当成修饰符报错。
5. 需要实跑输出（测试结果、命令输出）时，只在导出的临时目录里跑（见命令文件），不在项目里跑。

## 讲解源文件格式

讲解源文件是 Markdown 子集，结构固定，内容由你写：

````markdown
# <模块 id>：<一句话说清这个模块做了什么>

<两三句摘要：做了什么、核心在哪、先看哪里。会显示在页头的摘要框里。>

<details>
<summary>先懂这几个词</summary>

- **<术语>**：<一句话解释>

</details>

## 为什么改

## 产出清单

## 分层讲改动

### <第一层的意图，写成一句话>

## 阅读路线

## 需要你判断的

## 附录

（由脚本生成）
````

- 六个二级标题必须是这六个、按这个顺序。`附录` 只写那一行占位：文件表和提交表由渲染脚本生成。
- 支持：三到六级标题、段落、两层列表、表格、代码块、`<details>` 折叠、行内代码、粗体、`[文字](https://…)` 链接。
  不支持的写法（引用块、HTML、三层列表）会原样显示并被检查脚本提醒，不要用。
- **引用代码**：`[[路径:L12-L30]]`、`[[路径:L12]]`、`[[路径]]`。路径相对仓库根目录，行号按**终点提交上的文件**。
  路径里有 `[` 或 `]` 时（如 Next.js 的 `[[...slug]]` 路由目录），把路径放进反引号：``[[`src/app/[[...slug]]/page.tsx`:L10-L19]]``。
  渲染时变成链接；检查脚本会核对文件存在、行号不越界。
- **实跑输出**：写成代码块 ```` ```output O1 ````，第一行是 `$ <所跑的命令>`，后面原样贴输出（太长可截取，并写明截取了哪部分）；
  正文用 `[[out:O1]]` 引用它。**输出块放在讲到它的地方**：第一次引用之后，或讲解它的那一层里（AC 表引用了某层的输出块时，
  块放在那一层即可）；不要放进「附录」（附录内容不会显示，检查脚本判错）。一个输出块可以有几条命令，每条以 `$ ` 开头、后面跟它的输出。
  输出里的本机临时目录路径换成 `$TMP`。
  git 命令的输出也算实跑输出：没有文件行可引的事实（例如「终点之后还有一个发版提交」）就跑 `git log`／`git show --stat` 贴出来引用。
- **图**：```` ```mermaid <一句结论> ````，代码块的信息串就是图标题。

## 六节各写什么

### 为什么改

- 一两句话说这次要解决什么问题（来自 Spec 的目标，用你自己的话，不长段照抄）。
- **先写「分层讲改动」，再回来写 AC 表**：AC 表的「层」一列写层的编号（`L1`…），和三级标题开头的编号一致；跨几层就写「L1、L2」。
- **AC 表**（有 `module` 时必须有）：第一列表头写 `AC`，每个 AC 一行：要求（缩写）、落在哪一层、证据。
  证据只能是测试断言、代码行或实跑输出的引用；证据只覆盖一部分时照实写「只证明了一部分」并说明缺哪部分。
  Spec 的 AC 没有编号时（`acsNumbered: false`），按条目顺序写「第 1 条」「第 2 条」。
- 有 `usageDraft` 时，对照用法草案：计划的入口各做到了没有，计划外多做了什么。

### 产出清单

- **按项目类型分组**，不套固定类别。先看文件表判断项目类型，再选分组：
  - 前端：页面、组件、hooks／composables、公共函数、store、接口封装、样式与配置；
  - 后端或库：模块、类、公开函数、命令行入口、配置、迁移；
  - 插件或工具：用户碰得到的入口（命令、skill、自动触发的行为）、脚本与命令行、函数、规则文本与模板、测试。
- 每项写：新增还是修改、做什么、怎么用（签名、参数或调用方式）、代码位置（引用）、属于哪一层。
- 单独标出：改了签名或返回结构的；新增但仓库里没人调用的；Plan 没列却改了的文件。
- 有界面的页面附截图：在产出清单里这个页面那一项后面写一个截图块，标题是页面名，第一行是页面路径（以 `/` 开头，可带查询参数），
  命令会在终点提交上起服务截图；截不到时页面上自动写「截图未生成：原因」。只挑这次新增或明显改动的页面，最多 8 个。
  没有界面写「本模块无界面」，不写截图块。

### 分层讲改动

- 按**意图**把改动分成 3～7 层（三级标题），不按文件、不按提交分。每层标题以编号开头、写这一层的目的，如 `### L1 判据只在一个脚本里`。
- 每层讲清：这层改了什么、为什么这样做、和别的层怎么接上；关键处贴几行代码或引用。
- 核心逻辑（判据、状态转换、算法）要给一张「规则 → 代码行 → 测试」的表，或一个实跑实例，让读者能逐条核对。
- 只在图比文字清楚时画图，规则见下文。

### 阅读路线

- 有序列表，3～7 条，每条一个引用，按读懂的顺序排：通常先看一个真实的输入或用法，再看核心逻辑，再看入口怎么接上。
- 每条一句话说看什么、为什么先看它。

### 需要你判断的

列表，每条一个事实，带引用或实跑输出。只摆事实，不打分、不给修改建议。要找的东西：

- 偏离计划：Spec、Plan 写的与实际不一致的地方。引用两边：Spec、Plan 的那一行说明「计划写的是什么」，代码或测试的那一行说明「实际是什么」。
- 取舍：实现里做了的选择及代价（例如复用私有函数、吞掉异常）。
- 没测到的：Spec 要求了但测试没断言到的；只在一层测了的；错误分支没有用例的。
- 边界：出错时不会如实报告的地方（静默跳过、异常没接住）。能实跑验证就实跑，贴输出。
- 范围本身的疑点：facts 的 `warnings`、终点之后的提交、还没勾的项。
- 有独立审查结论时一起放进来；没有就写一条「没有独立审查记录」并引用 todo。

### 附录

只写占位，由脚本生成。

## 证据硬规则

- 每条证据只引用**测试断言、代码行或实跑输出**。**不照抄 Spec、Plan 或 todo 的原话当证据**——它们说的是计划，不是事实。
  可以引用 Spec、Plan、todo 的行来说明「计划或记录写的是什么」，但「做到了」必须另有代码、测试或实跑输出的引用。
  交付物本身就是文本的（规则、文档、模板、版本号），引用交付的那几行就算「代码行」；有测试断言它们的，优先引用测试。
  样张初稿的三处失真都出在这里：把 Spec 的「输出与旧版相同」当成测试证明了的；把「格式错或读不了」概括成「读不了」；数错提交数。
- 概括之前回到代码核对一次：条件分支接住了哪些异常、测试实际断言了什么，按代码写，不按名字或注释写。
- 拿不准的写「没有核实」，不要写成结论。
- 为验证边界在临时目录里构造的输入（新增或改动的文件）要在讲解里写明是构造的，并把构造内容贴进输出块。

## 选图规则

依据用户的《技术图表选型指南》：

- 先把读者的问题写成一句话，再选图：「由什么组成、谁调谁」→ 架构图（`flowchart` 加 `subgraph`）；「谁先谁后、传了什么」→ 时序图
  （`sequenceDiagram`）；「如果…就…」→ 流程图（`flowchart`，判断用菱形，每个出口标条件）；「变成什么状态」→ 状态图
  （`stateDiagram-v2`）；「数据从哪来到哪去」→ 数据流图（箭头上标数据名）。
- 一图一问；标题写结论（「判据只在 usage_draft.py 一处」），不写图名（「架构图」）。
- 每张图 5～12 个节点，多了就拆；一种箭头一种含义，混用时在图下用一句话说明；单一方向布局。
  超过 5 个节点优先上下布局（`flowchart TD`）：左右布局在手机宽度下会被压得看不清。
- 不分支的直线步骤用编号列表，不画图；两三项的对比用表格。
- 整页两三张就够；没有值得画的就不画。
- 图是代码的摘要：节点名用代码里的真实名字，图下给相关代码的引用。

## 里程碑页

`--milestone <M>` 生成的是里程碑页：模块页讲一个模块的细节，里程碑页讲这一站的模块**怎么串起来**。读者已经知道每个模块是什么（或可以点进模块页），
要的是全局：做成了什么、代码在哪、一次典型使用会经过哪些模块、模块之间新约定了什么。证据硬规则、选图规则、术语小注、引用写法都同模块页。

**读取策略**：范围往往很大，不整读 diff。顺序是：facts 的 `milestone`（用法、模块、各自范围）→ 用法草案里这一站的典型用法原文 →
各模块 Spec 的成功标准 → 输出目录里已有的模块页源文件（`<模块 id>.md`，有的话；它们的结论仍要回到代码核对一次才能引用）→
模块之间接口处的代码（一个模块输出、另一个模块读入的文件格式、字段、命令行参数、退出码）。

源文件格式：

````markdown
# <一句话说这一站做成了什么>

**一句话**：……

## 这一站做成了什么

## 代码地图

## 沿典型用法走一遍

## 跨模块约定

## 各模块讲解

## 需要你判断的

## 附录
````

### 这一站做成了什么

- 一张表：第一列以用法编号开头（`U1 模块交付后看讲解`），`milestone.usages` 里每个编号各占一行；第二列是证据（代码、测试或实跑输出的引用），
  写「这个用法现在真能这样用」的证据，不是「计划要这样」。
- 草案描述和实际不一致的地方写在表下，并放进「需要你判断的」。

### 代码地图

表由渲染脚本从 `codeMap` 画（目录、新增、修改、删除、未改），这里只写两三句怎么读：改动集中在哪、哪些目录是这一站新开的。不要自己再画表或列清单。

### 沿典型用法走一遍

- 选这一站最能代表的一个典型用法（说明选的是哪个），按它实际发生的顺序写成有序列表，**3～10 步**。
- 每一步：发生了什么、在哪段代码（引用）、属于哪个模块（正文写出**模块 id**，如 `brief-facts`）。跨模块的那一步写清交接的是什么（文件、字段、参数）。
- 模块里的细节点到为止，详细的留给模块页。

### 跨模块约定

- 这一站新出现的、不止一个模块都遵守的约定：文件格式、字段名、退出码、命名、目录位置、参数约定。
- 每条至少引用**两个不同文件**里的代码，证明确实有两处在用；只在一个模块里用的不算约定。
- 没有就整节只写一句「没有新约定」。

### 各模块讲解

表由渲染脚本生成（模块、职责、范围、状态、讲解页链接；没有模块页的写「还没生成」和生成命令）。这里最多写一句，比如推荐先看哪个模块页。

### 需要你判断的

同模块页；另外特别写：并集范围里夹进来的别的提交（看 `warnings`）、还没确认的里程碑、模块范围推断的疑点。

### 附录

只写占位，由脚本生成。

## 术语小注

列 3～8 个这次讲解里出现、但不在这个项目里工作的程序员可能不懂的词（项目自己的概念、缩写），每个一句话。没有就省掉整个 `<details>`。
